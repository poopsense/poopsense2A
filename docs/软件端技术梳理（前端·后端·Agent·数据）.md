# PoopSense 软件端技术梳理（前端·后端·Agent·数据）

> 这份文档从"每一端"的角度拆解软件系统，讲清**每端做什么、用什么技术、为什么这么选**。
> 和《项目总概述》的区别：总概述讲"这是什么"（给新人），这份讲"具体怎么做"（给开发/给自己复盘）。

---

## 1. 整体视图：五端 + 可审计事件主线

```
设备接入 → 采集会话 → 传感器观测 → 成员归属 → 健康评估 → Agent 行动 → 前端
                                  ↑          ↓
                               待认领箱   审计/反馈/重试
```

全系统的事实来源不是一张可随意覆盖的大表，而是五类可审计记录的组合：采集会话、传感器观测、成员归属、健康评估、Agent 行动。原始观测只增不改；用户认领、纠正、重新评估以新版本追加，保留来源和历史。

---

## 2. 设备接入端（数据怎么进来）

**职责**：把四传感器（毫米波/热成像/光谱/气味）的原始数据，变成一条结构化的采集会话包 JSON，送进后端。

**核心模块**：
- 数据采集（传感器读数）
- 边缘初筛（在设备/电脑侧算出 shape/color/odor 分类、特征摘要和质量信息）
- 上传（MVP 用 USB Serial；生产倾向 WiFi 直连云端）

**关键决策**：
- **数据契约当隔离层**——传感器型号随便换，只要最终 JSON 字段不变，后端和 Agent 一行不改。
- **边缘侧做分类、云端默认只收结果**——原始数据在设备本地短期滚动保存；只有用户专项授权后才限期上传，可撤回和删除。

**现状**：数据契约骨架已定，取值（颜色枚举/气味分档/member_id 来源）待硬件队友补齐。

## 3. 后端（数据怎么存、怎么管）

**职责**：接收、存储、管用户和家庭成员、算趋势、对外提供 API。

**核心模块**：
- **API 网关**：接收设备上传、给前端和 Agent 提供读接口。
- **鉴权与成员管理**：用户注册登录、家庭成员关系（管理员/被监护者/查看者）、授权可撤回。
- **可审计存储**：分别保存会话、观测、成员归属、评估和行动；原始观测不可覆盖，纠正以新版本追加。
- **成员待认领**：识别不可靠时进入家庭待认领箱，认领前不进入个人趋势、不生成定向推送。
- **趋势聚合**：按日/周/月计算频率、类别占比、连续异常、个人基线偏离和有效样本覆盖率；不对颜色或形状直接求平均。
- **可靠事件处理**：数据库事务同时写业务记录和 outbox；后台 worker 使用幂等键、指数退避的有限重试与失败状态，避免漏处理或重复推送。失败事件进入 `failed`/`dead_letter` 状态供告警和人工重放，重放沿用原幂等键。

**技术选型（建议）**：
- 语言：**Python（FastAPI）**——因为硬件侧本来就用 Python 读串口、跑 ML，后端也用 Python 全链路最顺。
- 数据库：**PostgreSQL**——用户、成员、家庭关系与五类事实记录都适合关系模型；MVP 阶段不用急着上专门的时序库，可按五类记录分表并用统一链路字段关联。

**关键决策（trade-off）**：为什么 MVP 不上时序数据库？——家庭场景数据量很小（一天几次），专门时序库（如 InfluxDB/TimescaleDB）是"将来量大了才需要的复杂度"，现在上是负担。等真到万人规模再迁移，迁移成本可控。

## 4. Agent 层（核心，最值钱）

**当前已落地（2026-08-27）**：`agent.py` 已实现第一条真实闭环。调用者先经家庭/成员授权检查；确定性规则生成风险走廊与 `allowed_actions`；只把该成员的 30 天汇总趋势和最近 5 次评估作为最小上下文交给 OpenAI-compatible 模型；模型回复、授权依据、策略/模型版本及调用结果持久化。模型未配置或供应商失败时明确失败，不降级成未经标识的假答案。

主动模式通过 `POOPSENSE_LLM_PROACTIVE_ENABLED` 显式开启。成员确认后写入 `agent.orchestration.requested` outbox；LLM 从规则白名单选择 `no_action / send_check_in / redline_notification` 等允许动作，后端严格校验返回 JSON，越界动作直接失败，合法行动仍走 `AgentAction + outbox + 发送前授权复核`。

**当前模型配置（2026-08-28）**：默认适配 DeepSeek OpenAI-compatible API，`base_url=https://api.deepseek.com`、`model=deepseek-v4-pro`，主动调度默认开启。API Key 只允许通过后端环境变量注入，绝不进入前端、数据库、日志或版本库。未配置 Key 时对话返回 `MODEL_NOT_CONFIGURED`，主动 outbox 不入队。

**用户可见性**：提供只读的模型状态、本人对话列表/历史和本人 Agent 行动接口。前端医生页自动恢复最近对话，“我的”页显示行动类型、状态和时间。接口始终以当前认证用户过滤 `recipient_id`，不会为了做通知中心而扩大到家庭全量审计数据。

**版本化记忆（2026-08-28）**：新增 `agent_memory_entries`。`self_report` 可由用户新增/修改，`system_inference` 可由用户纠正，`sensor_fact` 不允许覆盖；修改时旧行转为非当前版本并追加新版本。查看授权只授予读取，不自动授予编辑。LLM 最小上下文只读取当前有效版本，并保留来源和版本号，避免把推断冒充传感事实。

这里的“LLM 调度者”不是系统最高权限：它只能在规则产生的动作白名单里选择表达和后续建议。风险等级、数据可见范围、接收人和通知权限仍由确定性代码决定。可以把规则理解成带护栏的轨道，LLM 是轨道上的司机，司机不能把车开出轨道。

**职责**：让系统"主动做事"，而不是等用户问。核心是一个 5 步闭环。

**核心模块**：
1. **触发器**：事件到达 / 定时（晨间摘要）/ 异常检测（如连续多天 loose）→ 唤醒 agent。
2. **记忆**：分层——当前状态 + 历史档案 + 用户画像。MVP 由 PostgreSQL 保存权威版本，前端以类似 HEARTMEET 的可见可改界面呈现；以后可用 Mem0 辅助检索，但不替代权限、版本和审计。
3. **策略放行**：确定性规则决定风险、权限、接收人、通知频率和允许动作，LLM 无权修改。
4. **解释生成**：LLM 只在已放行动作内生成通俗解释，不决定是否披露或通知谁。
5. **工具执行**：执行前二次校验授权；记录输入摘要、策略/模型版本、接收人、授权依据、结果和幂等键。
6. **安全流程**：对已可靠识别的红线信号 100%进入安全流程；低置信度或缺失时明确显示“本次无法可靠判断”。
7. **分区记忆**：健康、宠物、社交模块使用不同数据视图和最小工具权限，不依赖 prompt 防止越权。

**技术选型（trade-off，重要）**：
- **MVP 不绑框架**：用最简 Python loop 手写闭环。理由：参赛原型（9/13）要的是"主动闭环"可演示，重框架（LangGraph/Letta）是学习/切换成本，负资产。
- **生产再上 LangGraph**：当需要"长流程、多分支、失败重试、合规审计/时间旅行回溯"时，LangGraph 的 checkpointer 才值得上。

**一句话记住**：**"agent 是循环、LLM 只是其中一环"**——触发、记忆、确定性策略、工具和反馈才是 agent 的真身，LLM 负责已放行范围内的解释与语言组织。

### 4.1 多 Agent 协同（怎么拆、怎么配合）

**为什么拆**：职责清晰 + 安全边界清晰（医疗建议和娱乐陪玩不能混在一个 agent 里）。代价：复杂度、记忆传递损耗、调试更难。

**拆 4 个**（一个调度 + 三个专职）：

| Agent | 职责 | 安全等级 |
| --- | --- | --- |
| 调度（主） | 触发→读记忆→判断谁管→分发→汇总→行动 | 中枢 |
| 健康（医生） | 解读数据给生活方式建议 | 最高（红线、不诊断） |
| 陪伴（宠物） | 形象、养成、打卡、陪聊 | 中（可萌，不给医疗建议） |
| 社交（交友） | 匿名卡片、匹配、AI 广场 | 最高（隐私、匿名化） |

**协同数据流**：触发 → 确定性路由优先判断"健康/陪聊/社交"（不明确时 LLM 仅提供路由建议）→ 专职 agent 读取获授权的最小数据视图并生成候选内容 → 策略与工具网关决定允许动作、接收人和频率 → 执行、审计并追加记忆版本。

**三个架构点**：① 统一身份、分区记忆（按用途提供最小数据视图）；② 策略与工具网关是唯一出口，所有动作二次鉴权并审计；③ 健康/社交采用更严格的数据和工具权限，陪伴模块也不能跨区读取健康原始数据。

**MVP vs 生产（trade-off）**：
- MVP 用"**一人多面 + 意图路由**"模拟（简单规则先判健康/陪聊/社交，判不了再 LLM 判），别真拆 4 个 agent——但**职责边界在代码里划清楚**（健康模块、陪伴模块、社交模块各自独立），将来要拆只是"搬模块"不是重写。
- 生产再真拆：LangGraph（多节点/子图，每 agent 一个子图）或 CrewAI（角色制，最贴合多专职 agent）。

## 5. 前端（用户看到什么）

**职责**：把数据和 agent 的行动展示给用户，4 个主导航区。

**核心模块**：
| 导航区 | 内容 | 技术要点 |
| --- | --- | --- |
| 首页 | 今日可靠结论 + 传感器映射形象 + Agent 医生入口 | 形象读取版本化 `visual_profile`，不是从 LLM 文案猜测或实时生成 |
| 健康 | 长期变化 + 健康档案（自报）+ 家庭共享 | 三条漫画式变化轨道 + 类别构成 + 可编辑档案 + 成员切换 |
| 社交 | 匿名卡片 + AI 广场 + 宠物 | 匿名化、只读档案 |
| 我的/设备 | 设备状态 + 登录入口 | 设备连接状态 |

**技术选型（决策）**：
- **出海 Web 优先**：先做响应式网站（手机+电脑通用），PWA 可装到桌面；后续 iOS → Android → 微信小程序复用同一套后端。
- 框架建议：**React + Tailwind**（生态最全）或 Vue（上手更简单），MVP 二选一都行。

**关键决策**：形象动画用"查表 + 播放预置动画"，不用"每次让 AI 生成图"——因为后者结果不稳定、还慢。可爱形象要的是"确定、快、可控"。

---

## 6. 运营/数据飞轮（横向，最易被忽略）

**职责**：追踪 agent 好不好，让它越用越准。

**核心指标**：
- 打开率（检测结果用户看不看）
- 采纳率（建议用户照做没）
- 每日复盘（今天建议准不准，写进 AGENT.md 第二天改进）

**关键决策**：没有这层，Agent 层就是"花架子"——这是三层壁垒里"运营驱动质量控制"的技术落地。

## 7. 数据模型（贯穿所有端的核心）

**五类数据共同构成可审计事实来源**

| 数据类别 | 作用 | 修改规则 |
| --- | --- | --- |
| 采集会话 `sessions` | 一次如厕的开始、结束、设备和家庭上下文 | 状态推进；完成后只追加修订 |
| 传感器观测 `observations` | 各维分类、置信度、缺失原因、来源和模型版本 | 原始观测只增不改 |
| 成员归属 `member_assignments` | 候选成员、置信度、认领/纠正历史 | 新版本覆盖生效，保留历史 |
| 健康评估 `assessments` | 规则风险、趋势指标、策略版本 | 规则升级后可重新生成新版本 |
| Agent 行动 `agent_actions` | 推送、报告、接收人、授权、执行与反馈 | 状态机推进，全程审计 |

设备上传的会话包示例：

```json
{
  "schema_version": "1.0",
  "session_id": "ses_001",
  "correlation_id": "cor_001",
  "device_id": "dev_001",
  "household_id": "hh_001",
  "firmware_version": "0.3.0",
  "model_version": "edge-0.2.0",
  "sequence_number": 42,
  "source": "device",
  "timestamp": "2026-08-22T08:30:12+08:00",
  "end_timestamp": "2026-08-22T08:31:45+08:00",
  "duration_s": 93,
  "presence_state": "present",
  "collection_state": "completed",
  "observations": {
    "shape": {"value": "normal", "confidence": 0.76, "missing_reason": null, "source": "sensor", "model_version": "shape-0.1"},
    "color": {"value": "brown", "confidence": 0.82, "missing_reason": null, "source": "sensor", "model_version": "color-0.2"},
    "odor": {"value": "moderate", "confidence": 0.71, "missing_reason": null, "source": "sensor", "model_version": "odor-0.1"}
  },
  "temperature_c": 24.8,
  "humidity_pct": 63.1,
  "quality": {"overall_confidence": 0.74, "reasons": []},
  "member_assignment": {"status": "pending", "candidates": [], "confidence": null, "assigned_by": null, "assigned_at": null}
}
```

其中 `received_at` 由服务端在接收时写入，设备不得自行声明；服务端同时保存 `schema_version`、`session_id`、`correlation_id`、`device_id`、`household_id`、`firmware_version`、`model_version`、`sequence_number` 和 `source`，使同一会话从接入到行动可全链路追踪。

配套保存用户/成员、家庭、授权、设备身份和原始数据授权记录。`member_id` 由后端归属流程产生；硬件只能提供候选和置信度。未归属会话进入家庭待认领箱。

设备接入还必须覆盖首次配网与绑定、每设备独立密钥、密钥轮换、离线缓存与补传、服务器回执、时钟同步、固件升级/回滚、解绑和转售清除。

## 8. 技术选型总表（MVP vs 生产）

| 端 | MVP（9/13 前） | 生产 |
| --- | --- | --- |
| 设备接入 | USB Serial + Python 读串口 | WiFi 直连云端 |
| 后端 | FastAPI + PostgreSQL + outbox worker | 同左；达到明确吞吐瓶颈后再评估消息队列/时序扩展 |
| Agent | 最简 Python loop + 规则引擎 + LLM SDK + 文件记忆 | LangGraph + Mem0/Letta |
| 前端 | React/Vue 响应式网站 + PWA | iOS/Android 复用后端 |
| 部署 | 本地/单服务器 | 上云 + 监控 |

**原则**：**MVP 追求"最简可演示闭环"，生产追求"可靠、可回溯、可扩展"。别在 MVP 阶段堆生产工具。**

表中的“文件记忆”仅指用户可读写的呈现/导出形态；权威数据、权限、版本与审计仍存 PostgreSQL。

## 9. 端与端之间的接口（数据怎么流）

```
传感器 → 会话包 → 后端事务落库（session/observation + outbox）
                          ↓
               成员已确认？否 → 家庭待认领箱
                          是
                          ↓
               规则评估 → 策略校验权限和允许动作
                          ↓
               LLM 生成解释 → 工具二次鉴权并执行
                          ↓
              前端展示 + 用户反馈 → 审计并追加记忆版本
```

**关键架构点**：各端只通过后端 API 和受控事件交互，不互相私传健康数据。原始观测、归属修订、评估版本和行动审计共同形成可追溯事实链。

家庭查看授权同时约束读取与红线通知。撤回事务必须立即使授权版本失效，写入撤回事件，并让通知 worker 在真正发送前再次检查最新授权；尚未发送的旧任务标记为 `cancelled_by_revocation`，不得仅依赖任务创建时的授权快照。

**固定实现顺序**：可靠数据链路 → 成员认领 → 规则建议与趋势 → 主动通知与家庭授权 → 记忆 → 宠物 → 社交 → 多 Agent 编排。后续模块可以并行设计，但不得成为核心闭环的运行依赖。

## 10. 当前代码落地状态（2026-08-24）

代码位于 `backend/`。已完成 FastAPI 接口、SQLAlchemy 数据模型、设备密钥与绑定家庭校验、五类事实链起点、服务端接收时间、内容摘要幂等、待认领箱、家庭认证、认领纠正版本和事务 Outbox 写入。本地用 SQLite 快速验证，连接字符串切换后使用 PostgreSQL；SQLite 不是生产权威库。

第二开发单元已完成：Outbox worker 具备 `pending/processing/retry/succeeded/dead_letter` 状态、指数退避、有限重试、崩溃租约回收和保留原幂等键的人工重放；规则评估以新版本追加；趋势只纳入当前已确认归属且评估可靠的样本，并输出类别占比、频率、连续异常与有效覆盖率。

第三开发单元已完成：Alembic 管理生产表结构；用户、健康成员档案、家庭角色和 API 凭证分表；家庭查看授权按版本保留历史；撤回事务同时取消尚未发送的通知；worker 在发送前读取最新授权，竞态测试证明旧授权不能继续发送。开发期仍使用演示 API 密钥，后续接正式登录时替换凭证入口，不改变角色与授权表。

第四开发单元已完成：`frontend/` 使用 React + TypeScript + Vite，已接入成员目录、待认领、认领/纠正、趋势和记录历史接口；PWA manifest、图标和静态壳缓存已配置，健康 API 明确不进入 service worker 缓存。开发凭证使用 `sessionStorage`，不做长期持久化。

首页视觉映射已形成独立、可审计契约：成员会话读取形状、颜色、气味观测的值、置信度、来源和模型版本，规则映射出 `compact/elongated/scattered/irregular/uncertain`。只有评估可靠且形态属于已定义类别时才显示具体角色；低置信度、缺失或未知值一律显示不确定形象。前端角色素材只负责呈现，LLM 无权选择或覆盖形态。

# Panthera-HT 机械臂任务适配（2026-08-30 当前演示）

PoopSense 不让 LLM 直接控制电机。Agent 只能产生 `offer_water_pickup` 的受限能力信号；前端取得用户两次明确确认后，FastAPI 的 `RobotTaskService` 才能调用本机 Panthera-HT Host。当前固定状态机仅执行 `standby → pickup_approach → pickup → close_gripper → lift`，并在抬起位置保持；不调用 VBot、不移动、不进入交接位、不松爪。执行层负责真机模式校验、低速点到点运动、到位误差、超时与停止。

关键接口：`GET /robot/status`、`POST /robot/trajectories/deliver-water/poses/{pose}`、`POST /robot/tasks/pickup-water`、`GET /robot/tasks/{task_id}`、`POST /robot/tasks/stop`（均位于家庭作用域 API 下）。标定仍归独立上位机/管理流程，普通用户前端不展示关节角或轨迹编辑。
# 周报技术落地（2026-08-29）

- 数据表：`weekly_health_reports`，唯一键为 `household_id + subject_member_id + period_start`。
- 接口：`GET/POST /api/v1/households/{household_id}/members/{member_id}/weekly-reports`。
- 生成：7 日趋势事实 → 可靠性门控 → 确定性建议 → 可选 LLM 事实摘要 → 周报、Agent Action、用户通知同事务写入。
- LLM 调用失败不影响周报生成；低覆盖或少于 3 条可靠记录时固定进入 `insufficient`。
- 前端健康页支持加载、生成、错误显示和成员切换；展示策略版本与模型版本，避免把 LLM 文案伪装成传感事实。

## 原始数据隐私闭环（2026-08-29）

- `raw_data_authorizations` 保存用途、允许类型、保留期限、撤回和删除状态；`raw_data_uploads` 只保存对象引用与校验审计，不保存原始字节。
- 家庭接口负责授权、撤回、删除执行和状态查询；设备接口使用独立设备密钥，并对授权 ID、家庭、设备、类型和到期时间逐项校验。
- 对象键按设备唯一，重复同内容幂等；相同对象键内容变化返回冲突。
- 到期和撤回都会停止上传并进入删除流程，审计记录不会因删除原始对象而丢失。
