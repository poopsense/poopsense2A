# PoopSense 硬件对接说明（软件端 → 硬件队友）

## 0. 这份文档是干什么的

这是软件端（我）给硬件队友的一份对接约定。目的是把"硬件交给软件什么、软件需要硬件回答什么"说清楚，避免两边各自做、最后对不上。

**一句话：硬件负责产生带来源与置信度的观测，软件负责归属成员、评估、授权和行动。中间靠带版本的数据契约隔离。**

---

## 1. 双方边界（谁负责什么）

| 环节                  | 负责方 | 交付物         |
| ------------------- | --- | ----------- |
| 气味检测（BME688 + 气体分类） | 硬件  | 气味分类结果      |
| 颜色检测（光谱传感器）         | 硬件  | 颜色分类结果      |
| 形状检测（热成像）           | 硬件  | 形状分类结果      |
| 采集与上传（ESP32）        | 硬件  | 会话、分类结果、质量、版本和候选成员 |
| 数据接收与存储             | 软件  | 落库 + 档案 API |
| 形象/建议/趋势/游戏/社交      | 软件  | App 与 Agent |

**关键点**：软件不绑定具体传感器型号，但契约必须携带模型/固件版本、每维质量和来源。硬件不能把不可靠的成员猜测写成确定的 `member_id`。

## 2. 当前硬件进度（我了解到的，2026-08 同步）

| 指标 | 传感器 | 现状 |
| --- | --- | --- |
| 成员识别 + 起止 | 压力 + APDS9960 | 🟢 压力匹配成员、APDS9960 接近检测标记起止（约 15cm） |
| 气味 | BME688 | 🟡 能采湿度/气压/气敏电阻/温度；Bosch AI Studio 分类未跑通；已采酒精+空气各 30min 样本 |
| 颜色 | AS7341 光谱（无可见光） | 🟡 12cm 能测卡纸颜色；最小识别面积/范围未测 |
| 形状 | MLX90640 热成像 | 🔴 从头弄（理论上能分两端 1 vs 7，目标三档） |
| 通信 | USB | 🟡 USB 可用，BLE/WiFi 未定 |
| 供电 | USB | 🟡 未定最终方案 |

> 硬件整体还在 PoC 早期（硬件队友明确"到不了 PCB 打板"，要等基础功能/测量范围/传输协议确定）。这也解释了为什么硬件队友生病不影响软件开干。

**硬件开发思路（重要，影响软件架构）**：硬件"先在最理想化场景跑通（假设只有一坨粪便、无干扰），再叠加复杂因素"。这与软件"先用 mock 跑通闭环"是同一套工程哲学——分而治之，两边可并行。

**由此带来的软件架构要求：容错降级。** 软件不能假设每次都有完整可靠的 4 维数据：每维必须带 confidence 和缺失原因；缺失时链路继续运行但不得伪造默认值；关键输入不足时明确显示“本次无法可靠判断”，不以“可能”继续输出健康结论。`sample_quality` 的误导命名已在 v1.0 废弃。

## 3. 数据接口契约（核心，请硬件重点看）

### 3.1 硬件当前实际输出（2026-08-22 同步）

硬件队友同步的、Python 最终给 LLM 的 user message 长这样：

```json
{
  "event_id": "evt_001",
  "color_category": "brown_like",
  "color_confidence": 0.82,
  "odor_deviation": "moderate",
  "odor_change_pct": 31.2,
  "odor_confidence": 0.71,
  "temperature_c": 24.8,
  "humidity_pct": 63.1,
  "sample_quality": "usable"
}
```

**和我方目标契约的差距（需要硬件补的字段）**：

| 缺失字段 | 为什么必须补 | 建议 |
| --- | --- | --- |
| `member_candidates`（可选） | 为后端认领提供候选和置信度 | 波目前只做“有人/离开”；不能区分时返回空列表，不阻塞软件 |
| `timestamp` | 长期趋势靠时间，只有 event_id 不够 | 加 ISO 8601 时间戳 |
| `shape` | 形象化和建议都吃形状 | 三档粗分：`hard`(1-2)/`normal`(3-5)/`loose`(6-7)，精分 7 类待加表面纹理传感器 |

**目标会话包（软件接口 v1.0）**——颜色、气味和 shape 的具体取值仍待硬件确认：

```json
{
  "schema_version": "1.0",
  "session_id": "ses_001",
  "correlation_id": "cor_001",
  "device_id": "dev_001",
  "household_id": "hh_001",
  "firmware_version": "0.3.0",
  "model_version": "edge-0.2.0",
  "sequence_number": 42,
  "source": "device",
  "timestamp": "2026-08-22T08:30:12+08:00",
  "end_timestamp": "2026-08-22T08:31:45+08:00",
  "duration_s": 93,
  "clock_status": "synced",
  "clock_offset_ms": 120,
  "presence_state": "present",
  "collection_state": "completed",
  "observations": {
    "shape": {"value": "normal", "confidence": 0.76, "missing_reason": null, "source": "sensor", "model_version": "shape-0.1"},
    "color": {"value": "brown", "confidence": 0.82, "missing_reason": null, "source": "sensor", "model_version": "color-0.2"},
    "odor": {"value": "moderate", "confidence": 0.71, "change_pct": 31.2, "missing_reason": null, "source": "sensor", "model_version": "odor-0.1"}
  },
  "temperature_c": 24.8,
  "humidity_pct": 63.1,
  "quality": {"overall_confidence": 0.74, "reasons": []},
  "member_candidates": [{"member_ref": "m_001", "confidence": 0.58}]
}
```

> `received_at` 由服务端接收时写入，设备不得自行填充。`household_id` 可由已绑定设备携带，但服务端必须按认证后的 `device_id` 查询绑定关系并校验，不能把设备上报值当作授权依据。

需要硬件确认取值：① color 枚举；② odor 分档/绝对分类；③ shape 三档判定。无法给某一维时填写 `value: null`、低置信度与 `missing_reason`，不能伪造默认值。

**废弃 `sample_quality`（2026-08-24）**：硬件已澄清该字段实际表示 proximity，而非样本质量。v1.0 将其拆为 `presence_state`（人在不在）、`collection_state`（采集状态）与真正的 `quality`。旧字段只允许由兼容适配层读取，不得继续写入新接口。

**时长字段**：`timestamp` = 开始、`end_timestamp` = 结束、`duration_s` = 持续时间（秒）。时长来自 presence 会话起止点，是便秘的辅助信号，可能被玩手机等行为干扰，不能单独下结论。

### 3.2 字段说明（v1.0）

| 硬件字段 | 含义 | 备注 |
| --- | --- | --- |
| `schema_version` | 契约版本 | v1 首版为 `1.0`；兼容新增升次版本，破坏性变化升主版本 |
| `session_id` / `correlation_id` | 会话唯一 ID / 全链路追踪 ID | 配合设备 ID、序号做去重与排障 |
| `device_id` / `household_id` | 设备身份 / 绑定家庭 | 由安全配网与绑定流程建立 |
| `firmware_version` / `model_version` | 固件与边缘总模型版本 | 结果追溯与回滚依据 |
| `sequence_number` | 设备单调递增序号 | 发现重复、丢包与乱序 |
| `source` | 上报来源 | 设备固定为 `device`；人工补录由软件侧标记 `manual` |
| `timestamp` / `end_timestamp` | 坐下（开始）/ 起身（结束）时间 | 算时长用；长期趋势也靠 timestamp |
| `duration_s` | 如厕持续时间（秒） | 辅助信号，不能单独下结论 |
| `clock_status` / `clock_offset_ms` | 时钟同步状态 / 最近已知偏差 | 未同步时 `clock_offset_ms` 可为 null，发生时间按不可信处理 |
| `observations.*` | shape/color/odor 独立观测 | 每维包含 value、confidence、missing_reason、source、model_version |
| `temperature_c` / `humidity_pct` | 环境温湿度 | 环境上下文，非便便本体 |
| `presence_state` / `collection_state` | 人体存在 / 采集状态 | 两者不可再混入质量字段 |
| `quality` | 真正的总体采集质量 | 不替代各维质量 |
| `member_candidates` | 可选成员候选 | 只能给候选和置信度，最终归属由后端确认 |

**服务端补充字段**：`received_at` 是服务端可信接收时间，不属于设备上报载荷。服务端还应记录认证设备、绑定关系校验结果和原始载荷摘要，以便审计和排障。

**字段有效性规则**：

- 必填顶层字段缺失、类型错误、未知主版本或会话起止时间自相矛盾时，服务端拒收并返回可机器识别的错误码；不得静默补成“正常”。
- 单一观测缺失时保留会话，但该观测必须同时给出 `value: null` 和明确的 `missing_reason`；置信度若存在，范围为 `0`～`1`。
- 未识别的枚举值不得映射为最接近的健康类别，应作为未知值隔离并进入兼容性告警。
- `quality.overall_confidence` 只描述整次采集可用性，不得覆盖或推高任一 `observations.*.confidence`。

**成员归属约定**：硬件不再被要求直接提供最终 `member_id`。候选为空或置信度不足时，会话进入家庭待认领箱；用户认领前不进入个人趋势、不生成定向推送。

**要确认的颜色枚举**（硬件当前是 `brown_like`，请对齐成固定值）：`brown` 棕 / `dark_brown` 深棕 / `yellow` 黄 / `green` 绿 / `black` 黑 / `red` 红 / `clay` 陶土/灰白

**要确认的气味口径**：硬件现在给的是 `odor_deviation`（偏离基线程度）+ `odor_change_pct`（变化百分比），这是"和基线比变了多少"，不是"绝对属于哪一类"。请确认：最终是否还会输出一个绝对分类（如 正常/异常）？如果只有"偏离度"，软件要用它映射到"形象表情"和"建议"，需要约定偏离度分档（如 mild/moderate/severe 各对应什么）。

### 3.3 传输方式

- **MVP 用 USB Serial 即可**（当前已通），软件端读串口、解析 JSON。
- **最终走 BLE 还是 WiFi，请硬件尽快定**。这影响软件端是"实时接收"还是"攒一批再收"，以及要不要做断网缓存。
- **倾向建议：优先 WiFi 直连云端**。因为产品定位出海、先做网站，浏览器连 BLE 只有 Chrome 支持且不稳定；走 WiFi 后设备直接把数据发到云端，网站/App 统一从云端取，架构更顺。

无论最终使用 USB、BLE 还是 WiFi，协议都必须支持：服务器确认回执、设备端离线缓存、按 `device_id + session_id` 幂等补传、序号检测、时钟同步和有限重试。具体缓存容量、重试间隔和次数由硬件实测后冻结，软件不得先写死假参数。

**可靠性语义**：

- 设备只有收到服务端“已接收并持久化”的确认后才能把缓存记录标为可清理；网络超时或未知结果按同一幂等键补传。
- 相同 `device_id + session_id` 且载荷语义一致时返回原处理结果，不重复创建会话、评估或通知；若同一幂等键载荷不同，拒绝覆盖并记录冲突事件。
- `sequence_number` 用于发现重复、缺口和乱序，不能替代 `session_id`；离线补传允许乱序到达。
- 设备记录本地时钟及其同步状态/误差状态；时钟未同步时仍可上报，但必须标记时间不可信，服务端以 `received_at` 辅助排序且不得伪造精确发生时间。
- 缓存达到容量上限、数据损坏或最终重试失败时，设备必须暴露可诊断状态；不能悄悄丢弃后继续报告链路正常。

**设备身份与生命周期**：WiFi 生产方案必须包含首次安全配网、每设备唯一身份与独立密钥、密钥轮换和泄露吊销。绑定关系由服务端维护；解绑后设备立即失去原家庭数据权限并清除家庭标识、网络凭据、令牌和未上传原始数据。转售/恢复出厂不得保留前一家庭的凭据或数据。

**固件升级边界**：升级包必须验签、校验目标硬件与版本，防止降级到已撤销版本；安装失败可回滚到可启动版本。升级过程不得破坏尚未确认上传的会话，升级结果、固件版本和失败原因应可审计。固件与边缘模型可独立版本化，模型更新同样需要完整性校验和回滚能力。

### 3.4 原始数据与隐私

- 默认只上传分类结果、特征摘要和质量信息。
- 原始传感器数据在设备本地短期滚动保存，不默认上云。
- 只有用户针对算法改进明确授权后才可上传；授权记录包含用途、范围、保留期限和撤回状态。
- 每次上传必须能关联授权记录，并校验授权仍生效；不得用家庭查看授权、服务条款同意或默认勾选替代专项授权。
- 用户撤回或授权到期后立即停止新增上传，清理设备端待上传副本，并触发已上传数据删除流程。
- 删除过程记录 `requested`、`in_progress`、`deleted` 或 `failed` 状态和完成时间；失败需有限重试并可供用户查看/再次发起。法定必须保留的例外应单独说明范围与期限，不能继续用于算法训练。

### 3.5 特别要确认：气味与颜色口径

气味：硬件当前输出 `odor_deviation`（偏离基线程度）+ `odor_change_pct`（变化百分比）。请确认：
- 最终是否还会输出一个**绝对分类**（如 正常/异常/很臭）？如果有，枚举是什么？
- 如果只有"偏离度"，请给出偏离度的分档定义（如 mild/moderate/severe 各自什么阈值、对应什么含义），软件好映射到形象表情和建议。
- 暂测不了时可降级为"用户勾选气味"，数据里标 `source = manual`。

颜色：请把 `color_category` 的枚举固定下来（当前 `brown_like` 太模糊），并说明每个值对应什么真实颜色。

## 5. 联调里程碑（建议）

| 里程碑 | 内容 | 双方各做什么 |
| --- | --- | --- |
| L1 | v1.0 数据格式冻结 | 硬件按 §3 输出样例 JSON；软件确认版本、质量和去重字段 |
| L2 | 单传感器联调 | 先接一个（如颜色），验证字段对齐 |
| L3 | 三条 sensing 联调 | 完整档案落库成功 |
| L4 | 端到端闭环 | 检测 → 补传/去重 → 待认领 → 评估 → 形象/建议 → 展示/通知 |

### 5.1 联调验收场景

1. **正常上报**：完整载荷只形成一个会话，各维观测及版本可追溯。
2. **缺字段/类型错误**：顶层必填字段错误被明确拒收；单维缺失按 `value: null + missing_reason` 降级，不生成该维结论。
3. **低置信度**：保留事实和置信度，但软件明确显示“本次无法可靠判断”，不输出弱健康结论。
4. **重复上传**：相同幂等键与相同载荷返回原结果，不重复评估和通知；同键不同载荷进入冲突状态。
5. **离线补传**：断网期间缓存，恢复后允许乱序补传且用序号发现缺口；收到持久化确认后才清理缓存。
6. **成员未识别**：候选为空或不足时进入家庭待认领箱，认领前不进入个人趋势和定向推送。
7. **认领纠正**：硬件原始观测不被覆盖，归属纠正由软件新增版本记录。
8. **授权撤回/到期**：停止原始数据上传，清理待上传副本，云端删除状态可追踪。
9. **红线通知**：硬件只提供可追溯观测；是否进入红线安全流程及通知谁由软件确定性策略决定。对缺失或低置信度输入不得声称已可靠识别红线。
10. **升级与解绑**：升级失败可回滚且缓存会话不丢失；解绑后旧凭据不能继续上报到原家庭。

## 6. 版本约定

- 数据格式以本文档版本为准，变更需双方确认并更新版本号。
- 联调中字段调整，请先同步软件端，避免单方面改格式。
- 同一 `device_id + session_id` 的重传必须语义一致；服务器可重复接收但只能形成一份有效会话。
- `schema_version` 遵循主版本兼容边界：新增可选字段升次版本；删除字段、改变类型或语义必须升主版本。服务端只接受明确支持的版本，禁止猜测转换。
- 低置信度或缺失必须显式表达，不得填充看似正常的默认分类。

## 附录：布里斯托大便分型（Bristol Stool Scale）参考

> 当前产品只做三档粗分：hard（1-2 干硬）/ normal（3-5 正常）/ loose（6-7 稀）。完整 1～7 精分需额外的"表面纹理"传感器，作为后续路线图。

| 分型 | 形态 | 大致含义（仅作通俗参考，非诊断） |
| --- | --- | --- |
| 1 | 干硬球状 | 通常与缺水/纤维不足相关 |
| 2 | 干硬条状 | 偏干 |

## 2026-08-28 软件侧基线补充

个人基线由软件使用“已认领且可靠”的分类结果计算，硬件无需上传平均值或基线结论。硬件继续逐维提供分类值、置信度、缺失原因、模型版本和来源；历史可靠样本不足时软件不生成基线判断。本轮未修改硬件 JSON 契约，也未虚构颜色、气味或形状阈值。

## 2026-08-28 宠物单元边界

便便宠物、每日打卡、名字、皮肤和成长阶段完全属于软件域，不新增设备字段，也不改变硬件 JSON。宠物只消费服务端已经完成认领、质量门控和规则评估后的摘要；硬件不得上传 `pet_mood`、成长值或皮肤解锁结论。

## 2026-08-29 社区单元边界

ANP 社区完全属于软件公开内容域，不新增硬件字段。传感观测、设备 ID、候选成员、置信度和原始数据均不得自动进入公开帖子；硬件数据契约保持不变。

## 2026-08-29 多专家复核边界

多专家复核只消费服务端完成质量门控、认领和规则评估后的分区摘要，不新增硬件字段。安全仲裁不能反向修改设备观测、置信度或模型版本。

## 2026-08-29 Agent 匹配边界

Agent 匹配完全属于软件身份与同意域，不新增硬件字段，也不能以设备 ID、成员候选或传感结果作为匹配条件。
# 软件周报对硬件数据的使用边界（2026-08-29）

周报不新增硬件字段，也不替硬件推断阈值。它只消费已通过现有数据契约入库、已可靠评估且已归属成员的观测事实；未认领、缺字段、低置信度和无效采集不会被包装成周报结论。硬件重复上传由既有幂等链路消化，不会导致同一周重复生成报告。

## 原始数据上传门控（2026-08-29）

设备在上传原始光谱、热成像、气味或在场数据前，必须取得后端签发的专项授权 ID，并通过 `POST /api/v1/raw-data-uploads` 登记对象键、类型、字节数和 SHA-256。登记接口继续使用 `X-Device-Key`，授权 ID 不能代替设备身份。后端拒绝跨家庭、跨设备、未授权类型、已撤回和已到期请求；硬件应在拒绝后继续本地滚动策略，不应无限重试上传。
